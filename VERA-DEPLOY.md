# VERA connectivity prototype

The existing Vera Nexus service is connected to `vera-mvp`. Its `pip install -r requirements.txt` build installs `requirements-vera.txt`, and `python app.py` starts Gunicorn. `gunicorn.conf.py` runs the cloud call scheduler inside the same service. Keep the original main branch unchanged.

Set OPENAI_API_KEY securely in Render Environment and generate a separate long random VERA_ACCESS_TOKEN. The latter is required in the Authorization bearer header; never embed it in a distributed APK. No secrets in GitHub. Existing repository is public. Do not commit private data.

GET /health checks availability. POST /api/realtime/client-secret creates an ephemeral OpenAI Realtime credential for an authenticated client. Real audio and billing must be tested after credentials are configured. Gmail, durable cloud memory and cloud scheduling are outside this push integration. The shared bearer is for one private operator, not multi-user enrollment.

## Firebase Cloud Messaging

- Firebase project: `vera-nexus-e5119` (Spark). Android package: `tw.vera.nexus`. Firebase app ID: `1:1041608787597:android:e26a9db3e9039b2cd244c4`.
- Set the GitHub Actions repository variable `VERA_FIREBASE_ANDROID_CONFIG` to the registered app's Android client SDK config. For local builds, use `android/app/google-services.json`. Gradle rejects mismatched project, package, or Firebase app IDs. A build without the client JSON keeps local reminders and reports that Firebase is unavailable. Never place service-account JSON in the repository or the Android configuration variable.
- In Render's existing Vera Nexus service, add the dedicated FCM service account credential as the **Secret File** `vera-firebase.json`. The code discovers `/etc/secrets/vera-firebase.json` automatically unless `GOOGLE_APPLICATION_CREDENTIALS` is configured explicitly. Keep the service-account JSON out of the repository, APK, logs, and chat.
- If a persistent disk is approved, point `VERA_PUSH_DB` to a file on its mounted path, e.g. `/var/data/vera-push.sqlite3`. Without a disk, cloud schedules and receipts can disappear on deployment or instance replacement. The opted-in app re-enrolls on foreground use, token refresh and its periodic Android network job. Re-enrollment restores the device, not discarded cloud schedules.
- All four push operations require the existing VERA bearer. `POST /api/push/status` checks whether Render sees a credential file. `PUT /api/push/device` enrolls or rotates a device token. `DELETE /api/push/device` revokes an installation. `POST /api/push/dispatch` takes UUIDv4 `device_id` and `event_id`, optional `task_id` (opaque local task identifier) and optional `test`. Do not send legal case content through push. The 45-second message expiry, 24-hour server retry guard and device-side deduplication prevent stale or duplicate alerts within this prototype's storage limits.
- In **雲端 → 註冊此裝置**, enable notifications and register with a verified VERA login. **測試雲端來電** queues a test without microphone use. **遠端推播紀錄** distinguishes FCM acceptance, device receipt, ringing and final result. A FCM acknowledgement does not prove delivery. Repeat while backgrounded and screen-locked, then verify quiet hours, decline and opting out.
- The Cloud Connection Center creates or cancels calls through `/api/cloud/calls`. Phones report through `/api/cloud/receipt`. A recorded miss can queue one optional five-minute retry. The scheduler drops expired calls after an outage. After acceptance, the app can load the call purpose via `/api/cloud/context`. FCM messages only carry opaque IDs, expiry and test metadata.
